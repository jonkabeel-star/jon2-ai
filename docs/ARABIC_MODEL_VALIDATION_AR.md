# خطة التحقق الشاملة لعقل Jon2 — Safari وPython والجودة العربية

هذه الخطة لا تغيّر أوزان النموذج ولا تفتح المحادثة العامة. جميع ملفات checkpoint وmanifest وweights ومرجع logits وتقارير التقييم تبقى خاصة، ولا تُرفع إلى GitHub.

## بوابات لا يجوز تجاوزها

1. **سلامة الحزمة:** بصمة checkpoint وweights صحيحتان.
2. **تطابق tokenizer:** Python وSafari ينتجان token IDs متطابقة لكل prompt.
3. **تطابق النموذج:** قيم logits ضمن الحدود العددية المحددة، وأهم شيء أن greedy next-token يطابق Python.
4. **سلامة النص:** فلاتر السطح تمنع النصوص المكسّرة والتكرار الواضح. هذا ليس فهمًا للمعنى.
5. **التقييم البشري:** كل إجابة في مجموعة الاختبار تُراجع يدويًا بالفصحى والمصرية.
6. **إطلاق عام:** ممنوع حتى اجتياز كل البوابات وموافقة مالك المشروع صراحة.

## المرحلة A — اختبار تطابق Python وSafari على نفس checkpoint

المطلوب من نفس إصدار checkpoint:
- ملف checkpoint الأصلي الخاص.
- manifest.json وweights.bin الناتجان من تصدير Safari الخاص.
- بيئة Python بها PyTorch واعتماديات المشروع، وNode.js لتشغيل مدقق Safari.

### A1. تصدير مرجع Python

شغّل من جذر المستودع، مع استخدام مسارات الملفات الخاصة الموجودة في بيئتك:

~~~bash
python ai_engine/export_safari_parity_reference.py \
  --checkpoint /private/path/jon2-last.pt \
  --manifest /private/path/manifest.json \
  --output /private/path/python-reference.json
~~~

يمكن تمرير --prompt "النص" أكثر من مرة لإضافة أسئلة. المرجع يحتوي logits؛ لذلك يجب إبقاؤه خاصًا وعدم إضافته إلى Git.

### A2. مقارنة Safari

~~~bash
node scripts/verify_safari_parity.mjs \
  --manifest /private/path/manifest.json \
  --weights /private/path/weights.bin \
  --reference /private/path/python-reference.json
~~~

المدقق يوقف العملية إذا اختلفت بصمة checkpoint أو weights، أو اختلفت token IDs، أو اختلف greedy argmax، أو تجاوز خطأ logits الحدود العددية. حدود المقارنة الحالية: أقصى خطأ مطلق 0.002 وRMS 0.0005، مع تطابق الرمز التالي تمامًا.

### A3. تفسير النتيجة

- اختلاف token IDs: أصلح tokenizer أو pre-tokenization أولًا.
- token IDs متطابقة لكن logits تختلف: افحص تحويل الأوزان، ترتيب tensor، طبقات attention/normalization، أو اختلافات FP32/FP64.
- logits متقاربة لكن argmax مختلف: لا تعتمد التشغيل؛ اختلاف الرمز التالي قد يغيّر النص كله.
- تطابق كامل: يثبت التكافؤ العددي على prompts المختبرة فقط، ولا يثبت جودة العربية.

لا تُعدّل أوزان checkpoint لإخفاء فشل parity. أصلح التنفيذ ثم أعد المقارنة.

## المرحلة B — فلتر سلامة النص

الفلتر يفحص الحروف غير المدعومة، النواتج القصيرة جدًا أو الطويلة جدًا، التكرار، وكثرة المقاطع العربية القصيرة في إجابة طويلة. أضيفت حالات regression للردود المكسّرة التي ظهرت في الاختبار.

حدود مهمة:
- لا يمكن لفلتر regex أو إحصاءات الكلمات أن يثبت أن الإجابة مفهومة أو صحيحة.
- قد يرفض بعض النصوص السليمة؛ لذلك يجب مراجعة false positives.
- لا تُعرض إجابة مرفوضة للمستخدم على أنها إجابة ناجحة.
- لا يتحول اجتياز الفلتر إلى موافقة إطلاق.

## المرحلة C — تقييم الفصحى والمصرية

مجموعة الاختبار في ai_engine/evaluation/arabic_smoke_tests.json منفصلة عن بيانات التدريب. تحتوي أسئلة فصحى ومصرية في التعريف، الشرح، الحساب، الكتابة، وعدم اليقين.

شغّلها على checkpoint خاص:

~~~bash
python ai_engine/evaluate_arabic_checkpoint.py \
  --checkpoint /private/path/jon2-last.pt \
  --output /private/path/jon2-arabic-review.jsonl
~~~

كل سجل يتضمن السؤال، الرد الخام، تشخيصات سطحية، بصمة checkpoint، وحقول مراجعة بشرية. لا توجد علامة نجاح دلالي آلية.

### نموذج المراجعة البشرية

لكل سؤال سجّل:
- هل الرد مفهوم؟ نعم / جزئيًا / لا
- هل أجاب السؤال فعلًا؟ نعم / جزئيًا / لا
- هل العربية سليمة وطبيعية؟ نعم / جزئيًا / لا
- هل المعلومة أو الحساب صحيح؟ نعم / لا ينطبق / لا
- ملاحظات على التكرار أو الاختلاق أو خروج الرد عن الموضوع.

أي إجابة غير مفهومة أو خاطئة في سؤال أساسي تعني أن checkpoint لا يجتاز إطلاق المحادثة العامة. احتفظ بالتقرير مع بصمة checkpoint حتى تكون المقارنة بين الإصدارات عادلة.

## المرحلة D — تحسين التدريب عند الحاجة فقط

لا تبدأ تدريبًا جديدًا قبل ثبوت parity. إذا نجح parity وفشل التقييم البشري، فالمشكلة في النموذج أو بياناته لا في Safari.

ترتيب التحسين:
1. تدقيق حقوق كل مصدر وتثبيت موافقة خاصة مرتبطة ببصمة SHA-256 للملف نفسه.
2. مراجعة اللغة والدقة والتكرار والتوازن بين الفصحى والمصرية، وإزالة الحشو.
3. إعداد مجموعات منفصلة للتدريب والتحقق والاختبار، مع فصل المحادثات/المصادر لمنع تسرب أمثلة الاختبار.
4. زيادة حجم البيانات المسموح بها فعليًا، لا بتكرار النصوص أو نسخ محادثات خاصة.
5. تدريب checkpoint جديد باسم وإصدار جديدين؛ لا تستبدل jon2-last.pt الحالي.
6. مقارنة loss على validation، ثم تشغيل مجموعة الاختبار البشرية نفسها دون تعديلها.
7. إعادة تصدير Safari bundle من checkpoint الجديد ثم إعادة اختبار parity من البداية.

### شرط مهم بشأن حجم النموذج

زيادة عدد المعاملات وحدها لا تصنع ذكاءً. النموذج الأكبر يحتاج بيانات أكثر بكثير، وذاكرة GPU، ووقت تدريب، وتقييمًا مستقلًا. لا تبدأ ملف 30M أو تدريبًا طويلًا اعتمادًا على مجموعة صغيرة أو مصدر غير معتمد.

## حالة الإطلاق

حتى وجود تقرير parity ناجح ومراجعة بشرية ناجحة وموافقة صريحة، تبقى:
- المحادثة العامة مقفولة.
- checkpoint الحالي محفوظًا دون تغيير.
- أي نشر أو دمج أو تغيير في Cloudflare متوقفًا.
- لا يوجد fallback إلى نموذج خارجي أو ردود وهمية.
